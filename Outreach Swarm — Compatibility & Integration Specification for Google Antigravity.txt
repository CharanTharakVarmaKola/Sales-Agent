## 1. Decision summary

**Build LangGraph as the primary router, OpenClaw as the skill runtime and secondary runtime-spawner, Obsidian as the sole durable memory, Paperclip as telemetry-only, and a single custom MCP sender service as the only outbound path.**

The pairing wins over any single-framework choice for one reason that is visible in source, not in prose: the two frameworks are strong in *disjoint* places, and each one's weak place is exactly where the other is strong.

- LangGraph owns **routing**. Its fan-out primitive is a first-class object, not a convention: `class Send` at `libs/langgraph/langgraph/types.py:732` is documented as "used within a `StateGraph`'s conditional edges to dynamically invoke a node with a custom state at the next step," the map-reduce example at `types.py:755-765` returns `[Send("generate_joke", {"subject": s}) for s in state["subjects"]]`, `Command.goto` is typed `Send | Sequence[Send | N] | N` at `types.py:852`, and the Pregel runner's real handling is `sanitize_untracked_values_in_send` returning `Send(node=packet.node, arg=sanitized_arg, timeout=packet.timeout)` at `pregel/_algo.py:1443-1460`, with dispatch fed by `sends: Sequence[Send] = channels[TASKS].get()` at `_algo.py:967`. That is a **verified** dynamic fan-out path.
- LangGraph also lets us satisfy the memory boundary in one line. `checkpointer` is an optional constructor argument defaulting to `None` (`pregel/main.py:733`, resolved through `ensure_valid_checkpointer` at `:798`), and `SqliteSaver` is a class that **requires** a `sqlite3.Connection` to exist at all (`libs/checkpoint-sqlite/langgraph/checkpoint/sqlite/__init__.py:45`, `__init__(self, conn, *, serde=None)`). Omitting the argument is therefore a real, enforceable disablement — not a configuration hope.
- OpenClaw owns **skill execution and isolation**. Its system prompt is assembled from a base prompt plus a literal `<available_skills>` XML block built by `formatSkillCatalog` at `src/skills/loading/skill-contract.ts:102`, exported as `formatSkillsForPromptCore` at `:135`, and reached through `resolveSkillsPrompt` at `src/skills/loading/workspace-skill-prompt.ts:213`. And per-agent isolation is real: `src/commands/agents.commands.add.ts:1` states it "Implements `openclaw agents add`, including config mutation, workspace setup, auth copy, and route binding setup," carrying its own `workspace` (`:62`), `agentDir` (`:65`), a per-agent auth profile store loaded from that `agentDir` (`:81`), and conflict detection that prints "Skipped bindings already claimed by another agent" (`:210`).

Neither framework can be the whole answer. LangGraph has no skill gating, no per-agent workspace, and no channel binding. OpenClaw has no typed fan-out graph, and its own durable state is a per-agent SQLite session — which your boundary #1 forbids as a lead store. Pairing them, with Obsidian as the arbiter, is the only arrangement where every non-negotiable is enforced by a mechanism you can point at.

**What this decision costs you:** two runtimes to supervise, one extra process to keep alive on Windows, and a serialization boundary between them (the nine-field result contract in §4). That cost is smaller than the alternative, which is bolting skill isolation and workspace partitioning onto LangGraph by hand.

**Q1 answered:** the pairing is confirmed by source. The decisive asymmetry is that LangGraph's flexibility (`Send`) and OpenClaw's isolation (`agents add` → own `agentDir` + own auth profile store) are each verified in code, while neither framework offers the other's mechanism.

**`verify_node` wrapper: IMPLEMENTABLE, CONFIRMED.** Because a conditional-edge function may return any sequence of `Send` objects, and because every node's return value flows through the same channel-write machinery (`pregel/_write.py:50` `writes: list[ChannelWriteEntry | ChannelWriteTupleEntry | Send]`), a wrapper that calls `action_fn(state)`, re-reads Obsidian, and rewrites `next_action` is a plain function composition. **Verdict:** a graph *can* run on ephemeral state and rehydrate durable state from Obsidian MCP tools. Restart recovery must therefore be our own function, not a checkpoint replay. ## 6. Obsidian-only memory and restart-recovery design

**Folder contract** (mirrored in `vault-schema/00-Schema.md` and `vault-schema/Templates/Lead.md`):

```
Outreach/
├─ Leads/<lead_id>.md          # frontmatter = authoritative compliance record
├─ Campaigns/<campaign>.md     # sequence definitions, offer, angle variants
├─ Patterns/<pattern>.md       # cross-lead learned patterns
├─ Operations/
│  ├─ Incidents/               # watchdog + compliance incidents
│  ├─ Sender-Health/           # per-identity capacity, halt windows, warmup stage
│  └─ Inference/               # inference_paused records
└─ Templates/Lead.md
```

**Write ownership — enforced in code, not convention.** `orchestrator/nodes/reporter.py` defines `WRITABLE_FRONTMATTER = {sequence_stage, last_contacted_at, sends_total, replies_total, best_performing_angle, conversation_stage, groundedness_avg}` and `TERMINAL_FRONTMATTER = {unsubscribed, bounced, do_not_contact, jurisdiction_hold, hard_bounce_count}`. `LeadReporter.report()` raises `ValueError` if a caller attempts to write either a terminal field or any non-allowlisted field. The outreach agents physically cannot move a lead into or out of a terminal state.

**Section-write discipline.** `Run Log`, `Replies`, `Incidents` are append-only via heading-targeted PATCH with `If-Match`; `Outreach Draft` is overwritten each attempt; frontmatter compliance fields are written only by the reply classifier or an operator. A full-note rewrite is never used for a lead note — that is what makes concurrent agents safe.

**Per-lead reporter — atomic patch, not a rewrite.** `ObsidianClient.patch_section()` issues:
```
PATCH /vault/Outreach/Leads/<lead_id>.md
Content-Type: text/markdown; charset=utf-8
Operation: append
Target-Type: heading
Target: Run Log
Create-Target-If-Missing: true
If-Match: <content-hash from read_note>
```
The version token is the plugin's own content hash, documented at `mcpHandler.ts:1296` ("`version` is a content hash of the file — pass it back as `vault_patch`'s `ifMatch` to make an edit conditional on the file being unchanged"). `ObsidianClient.read_note()` returns `(body, version)`; `LeadReporter.report()` re-reads after the patch to capture the post-write version. A concurrent edit fails loudly rather than being clobbered.

**Q5 answered — who may persist what:**

| Component | Persistence class | May persist | Must never persist |
|---|---|---|---|
| **Obsidian** | Durable | Leads, campaigns, patterns, operations, incidents, suppression/bounce/unsubscribe state, conversation history, reports, sender health | — |
| **OpenClaw per-agent SQLite** | Ephemeral | Session transcript, working context for the current run | Anything not mirrored to Obsidian in the same turn |
| **LangGraph checkpoints** | Ephemeral (**and disabled**) | Nothing — `checkpointer=None`; `SqliteSaver` never constructed | Anything |
| **Paperclip** | Operational telemetry | Run status, duration, stdout/stderr excerpts, cost/usage, heartbeats, liveness | Lead records, campaign knowledge, learned patterns, suppression state, conversation history, tokens |
| **OmniRoute / FreeLLMAPI** | Operational | Provider quota caches, key health | Lead data |
| **mcp-servers/email-outreach** | Operational | Send audit log (message id, timestamp, identity) | Lead content beyond the send payload |

**Q6 answered — restart-recovery plan (Obsidian only).** On process start, `restart_recovery()` performs four reads and consults **no framework checkpoint**:

1. **Enumerate** `Outreach/Leads/*.md` via `vault_list` / `search_query` with `type: lead`.
2. **Load terminal set.** For each lead, `parse_frontmatter()` (`obsidian_client.py`) extracts the four terminal booleans and `hard_bounce_count`. Any truthy value → the lead enters the terminal set and is **never queued**. This mirrors the gate exactly: the same fields, the same truthiness rule, so a lead that was blocked before the crash is blocked after it.
3. **Restore pacing** from `sequence_stage`, `last_contacted_at`, `sends_total`. Per-identity daily counters are reconstructed by counting `Run Log` entries whose `status=ok` and `policy=allow` for that identity on the current date — the run log is the ledger.
4. **Restore fleet state** from `Outreach/Operations/Sender-Health/*.md` (per-identity `daily_cap`, `phase0_status`, `in_halt_window`) and `Outreach/Operations/Inference/*.md` (`inference_paused`).
5. **Assert** that no framework store was consulted: the recovery function must not import `langgraph.checkpoint`, and `orchestrator/main.py` already runs `assert_no_llm_imports()` on the compliance module to prove the rigid plane stayed clean.

Because the compliance gate re-reads the note *immediately before every send* anyway, a stale in-memory state after recovery cannot produce a prohibited send — it can only produce a duplicate attempt, which the run-log ledger and `last_contacted_at` suppress.

## 7. Sender service design: Zoho/Gmail/AgentMail OAuth REST only

**One path, one token holder.** `mcp-servers/email-outreach/server.py` is the only module in the system that holds a refresh token or opens an outbound HTTP connection. |---|---|---|---|---|
| Zoho (×5) | `POST https://{host}/api/accounts/{accountId}/messages` | `ZohoMail.messages.CREATE` | `build_zoho_payload()` → `{fromAddress, toAddress, subject, content, mailFormat: "plaintext", askReceipt: "no"}` | UNVERIFIED — Phase-0 gate 1 |
| Gmail (×1) | `POST https://gmail.googleapis.com/gmail/v1/users/me/messages/send` | `gmail.send` (**send-only, not `gmail.modify`**) | `build_gmail_payload()` → base64url RFC 2822 in `raw` | UNVERIFIED — Phase-0 gate 1 |
| AgentMail (fallback) | `POST https://api.agentmail.to/v1/inboxes/{inbox_id}/messages/send` | API key (2 free accounts × 3 inboxes) | `{to, subject, text}` | UNVERIFIED — Phase-0 gate 2 |

**Q7 answered — the hard send-gate implementation, in exact order.** This is `send()` in `server.py`, and the order is the design:

1. **Re-read current state.** `client.read_frontmatter(lead_id)` — never cached frontmatter, never planning-time state.
2. **Block on terminal states.** `evaluate(fm, identity=…, identity_state=…)` runs the rigid plane: missing required field → `suppress_capacity`; any of `unsubscribed`/`do_not_contact`/`bounced`/`jurisdiction_hold` truthy → `suppress_<field>`; `hard_bounce_count >= 1` → `suppress_bounced`. A blocked result returns `http_status: 403` and **returns before any URL is constructed**.
3. **Validate sender capacity and health.** Same call: `phase0_status != "pass"` → block; `in_halt_window` → `suppress_halt_window`; `healthy is False` → block; `sent_today >= daily_cap` → block; `sent_today >= hard_ceiling_per_identity` → block.
4. **Validate compliance fields.** Presence of all six required fields (`unsubscribed`, `bounced`, `do_not_contact`, `jurisdiction_hold`, `consent_basis`, `sender_identity`) is checked first, and a *missing* key is a block — not an implicit `false`. This closes the "absent field reads as not-suppressed" hole.
5. **Send only through the OAuth REST wrapper.** Provider is resolved from the identity prefix; the refresh token is read from the *sender process's* environment; `calls.append(f"POST {url}")` happens **before** the HTTP call so a crash still leaves evidence of intent.
6. **Append the result to Obsidian.** `LeadReporter.report()` appends one `Run Log` entry via the atomic section patch, in the same turn.

**Instrumentation that makes the gate testable.** `send()` accepts `external_http_calls: list[str]`; Phase-0 gate 5 asserts this list is **empty** for a suppressed lead. The gate is not "we believe it blocks" — it is "zero URLs were constructed."

**Warm-up ladder, encoded in `config/send-policy.yaml`:** `stage_1: 2` → `stage_2: 7` → `stage_3: 12` per identity per day, `hard_ceiling_per_identity: 17`, randomised delays `45–210 s`, `allowed_local_hours: [8, 18]`. Advancement requires `min_replies: 3`, `max_bounce_rate: 0.02`, `min_days_in_stage: 3` — outcome metrics, never elapsed time. Halts: `bounce_cluster` (≥2 hard bounces in 10 min fleet-wide → 24 h), `http_429` (any 429 → 24 h), `suppression_anomaly` (suppression write fails or readback mismatches → 24 h).

## 8. Paperclip monitoring and watchdog design

**Adapter selection (justified in §4.5):** `openclaw_gateway` for OpenClaw workers (real run state), `process` for the LangGraph orchestrator (local long-lived process; the only documented disqualifier — no cross-run session persistence — is irrelevant because Obsidian holds state). `http` is rejected: its own doc says "When Not to Use — If the agent runs locally on the same machine." Manifests live in `paperclip-adapter/adapter.json`.

**Telemetry write:** `paperclip-adapter/heartbeat.py` posts `{agentId, status, timestamp, dryRun, inferencePaused, sendWarmupStage}` plus a `_forbidden_keys_absent` assertion list naming `lead_id`, `email`, `unsubscribed`, `bounced`, `conversation`. The watchdog self-test fails if any forbidden key appears — the boundary is machine-checked, not documented.

**Watchdog (`watchdog/watchdog.py`)** — required because Paperclip's outbound alerting remains unconfirmed:

- **Poll:** `GET {PAPERCLIP_BASE_URL}/api/activity` every `WATCHDOG_POLL_SECONDS` (default **90**, within your 60–120 s window).
- **Detect:** `detect_failures()` filters the status set derived from source — `{failed, timed_out, interrupted, cancelled}` — ignoring `succeeded`/`completed`/`running`/`queued`.
- **Dedupe:** `DedupeWindow(minutes=30)` keyed on `agent_id + "::" + fingerprint`. The fingerprint is `sha256(f"{agent_id}|{error_kind}|{normalised_message[:400]}")[:16]`, with whitespace collapsed so a flapping agent that varies whitespace still dedupes. Verified in self-test: first occurrence not a duplicate, second within the window is, and the fingerprint is stable under whitespace normalisation.
- **Incident note:** written to `Outreach/Operations/Incidents/<UTC-stamp>-<agent_id>-<fingerprint>.md` with YAML frontmatter (`type: incident`, `agent_id`, `error_kind`, `error_fingerprint`, `run_id`, `detected_at`, `severity`) and a checklist (inspect run / confirm no partial sends / clear halt window if armed).
- **Notify:** default is a **desktop toast** via PowerShell `System.Windows.Forms.MessageBox` — deliberately *not* an email, because an alert email would consume sender warm-up budget and could itself trigger the 24 h 429 halt. The email path is opt-in via `WATCHDOG_ALERT_VIA_EMAIL=true` and is delegated to the sender service, which owns the token.

**Why a toast by default is the right call:** your brief allows "one identity's own REST email API or a desktop toast." Choosing the toast preserves the warm-up ladder and avoids a self-inflicted 429 — a failure mode where the alerting mechanism causes the outage it reports.

## 9. Supervisor chat-console design

**Separation is structural, not cosmetic.** The supervisor console is a *read-only* natural-language surface. It has no send capability, no token access, and no write path to lead frontmatter.

- **Read surface:** Obsidian (`vault_read`, `search_query`, document-map tool, tags tool) + Paperclip (`GET /api/activity`, `/api/agents`, `/api/dashboard`). No write tools are mounted.
- **Query shapes it must answer:** "which leads are in a terminal state and why," "which identities are inside a halt window," "what is today's send count per identity," "what patterns have we learned across leads" (reads `Outreach/Patterns/`), "why was this lead blocked" (reads the `Run Log` + `Incidents` sections and quotes the `policy` reason verbatim).
- **Grounding rule:** every answer must cite the note path and section it came from. The console quotes the `policy_result.reason` string the gate actually produced; it never paraphrases a block reason into a summary that could drift.
- **What it must refuse:** "send X to Y," "mark this lead unsubscribed," "clear the halt window," "skip the compliance check." Each of those is either a sender-service call (not mounted) or a terminal-field write (rejected by `LeadReporter`). The refusal is architectural — the tools simply are not present.
- **Escalation sink:** the console is where `next_action="escalate_to_human"` results surface (produced by `verify_node` after `MAX_REWRITE_ATTEMPTS = 2` failed rewrites), because a lead that cannot be grounded needs a human, not another model call.

## 10. Antigravity configuration and MCP permission plan

**Q2 answered — no-source-modification MCP calls, per target:**

| Target | MCP call possible without source modification? | Evidence / caveat |
|---|---|---|
| **Obsidian's built-in MCP server** | ✅ **Yes** | The plugin ships MCP natively: manifest describes "A secure REST API and Model Context Protocol (MCP) server for your vault"; `POST /mcp/` with sessionless revision `2026-07-28` (`constants.ts` `MCP_SESSIONLESS_PROTOCOL_VERSION`). Point Antigravity at `http://127.0.0.1:27124/mcp/` |
| **Custom `email-outreach` MCP sender** | ✅ **Yes — but it is *our* code** | `mcp-servers/email-outreach/server.py` exposes `send_outreach_email` via FastMCP. No vendor source is modified; we author a new server |
| **Paperclip monitoring/read endpoint** | ⚠️ **Partly — HTTP read, not MCP** | Paperclip exposes REST routes (`routes/activity.ts`, `agents.ts`, `dashboard.ts`) but **no MCP server was found**. Wrap those reads in a thin MCP server, or have the supervisor console call REST directly. The adapter path (`openclaw_gateway` / `process`) is Paperclip's own integration mechanism and requires no source modification |
| **AgentMail's `agentmail-mcp` skill** | ✅ **Yes** | The skill's own doc points at the hosted Streamable HTTP server `https://mcp.agentmail.to/mcp`, with OAuth ("Use OAuth. Do not put an empty API key in the configuration"). Skill is vendored into `skills/agentmail-mcp/`; no vendor source modified |

**Q3 answered — Windows launch and supervision.** `start.ps1` performs ordered bring-up and prints exactly one PASS/FAIL line per service, exiting non-zero on any failure. Order and rationale:

1. **Obsidian REST reachability** — first, because everything else depends on memory. A 401 still counts as PASS (the plugin is listening; the key just was not sent).
2. **OmniRoute** (`pnpm start` in `vendor/OmniRoute`, probe `{OMNIROUTE_BASE_URL}/models`).
3. **FreeLLMAPI** (`pnpm start` in `vendor/freellmapi`, probe `/models`; default port 3001).
4. **ClawHub assertion** — `OPENCLAW_ALLOW_CLAWHUB` must be `false`, checked *before* the gateway starts.
5. **OpenClaw gateway** (`openclaw gateway run`, probe `/health`).
6. **LangGraph orchestrator** (`python -m orchestrator.main --startup-check`, expecting `orchestrator alive`).
7. **Paperclip dashboard** (`pnpm dev` in `vendor/paperclip`, probe base URL).

Paperclip supervises the orchestrator through the **`process`** adapter (`adapter.json`), which injects `PAPERCLIP_AGENT_ID` / `PAPERCLIP_API_KEY` and uses exit code for success/failure. OpenClaw workers are supervised through **`openclaw_gateway`**. Secrets are loaded from `.env` into the *process* environment only (`[Environment]::SetEnvironmentVariable(..., "Process")`) — never written to machine or user scope.

**Q8 answered — Antigravity MCP configuration, permission policy, Ask vs Allow, and token isolation.**

| MCP server | Transport | Mounted tools | Default |
|---|---|---|---|
| `obsidian` | `http://127.0.0.1:27124/mcp/` | `vault_read`, `vault_patch` (append-only, allowlisted headings), `search_query`, `vault_list`, document-map, tags, commands-list | **Allow** the reads; **Ask** on every `vault_patch` |
| `email-outreach` | stdio (our server) | `send_outreach_email` | **Ask** always. Never Allow |
| `paperclip` | thin MCP over REST (or direct REST) | activity/agents/dashboard reads; heartbeat write | **Allow** reads; **Allow** heartbeat (telemetry only) |
| `agentmail` | `https://mcp.agentmail.to/mcp` | send/check/manage/MCP skills | **Ask** on send; **Allow** on read; **Deny** `manage-inboxes` for outreach agents |

**Denied outright, at the platform level:** arbitrary shell, arbitrary HTTP/fetch, unrestricted filesystem, and any tool that returns a credential. The reason is not stylistic: an agent that can fetch arbitrary URLs can exfiltrate lead data, and an agent with a shell can read `.env` and every refresh token in it.

**How token isolation is actually achieved** (three independent mechanisms, so no single failure is fatal):
1. **The sender service owns the tokens.** `_refresh_token()` reads from `os.environ` *inside the sender process*; the value is never returned, logged, or placed in a tool result.
2. **Agents call MCP, not HTTP.** There is no HTTP tool in an agent's toolset. The only way out is `send_outreach_email`, which runs the compliance gate first.
3. **The policy token is server-side.** The gate reads the lead note itself; an agent cannot pass a "suppression checked: true" flag, because no such parameter exists.

**Filesystem policy:** agents see the repo root read-only plus their own workspace. `.env` is outside every agent-visible path. `config/` is read-only to agents (the allowlist is not agent-editable).

**Permission principle:** *Ask* on anything that leaves the machine or mutates durable memory; *Allow* on reads. That maps cleanly onto the boundary list — the two irreversible categories are sends and writes, and both get a human-visible confirmation path (the send via the MCP Ask prompt; the write via `If-Match`, which fails loudly on conflict).

## 11. Phased build plan, in exact implementation order

### Phase 0 — validation gates (hard-blocking; do not proceed until all eight pass)
1. **Zoho Free-plan OAuth/API entitlement, per account** — `scripts/phase0/validate_zoho.ps1 -Identity 01..05`. Mints an access token from the refresh token at `accounts.zoho.com/oauth/v2/token`, enumerates accounts, probes capability. Run with `-SendTestMessage` for the full `messages.CREATE` probe (self-addressed, zero external recipients). **If any account fails → activate AgentMail failover.**
2. **AgentMail failover** — `scripts/phase0/validate_agentmail.ps1`. **Blocking precondition, not automated:** read AgentMail's ToS and confirm two free accounts for one operator are permitted; the script refuses to run until `AGENTMAIL_TOS_MULTI_ACCOUNT_CONFIRMED=true` is set. Two signups → 3+3=6 inboxes, use 5. If ToS disallows → 3 AgentMail identities + passing Zoho/Gmail, rotation recomputed. The script also asserts each of the four vendored skills carries a `metadata.openclaw` gate.
3. **Reviewed model allowlist** — `scripts/phase0/validate_allowlist.py`. Every allowlisted model answers; a non-allowlisted probe is refused; exhaustion reports `inference_paused`. Leave `globalFallbackModel` unset (see §4.3).
4. **Obsidian MCP roundtrip** — `scripts/phase0/validate_obsidian_roundtrip.py`. Writes via section patch, reads back exact match, logs both to Paperclip.
5. **Compliance gate** — `scripts/phase0/validate_compliance_gate.py`. Suppressed lead → `403 SUPPRESSED`-equivalent, `external_http_calls=0`.
6. **Verification loop** — `scripts/phase0/validate_verification_loop.py`. Missing `role` → verifier rejects, retry fires, terminal `escalate_to_human`.
7. **Dynamic spawn** — `scripts/phase0/validate_spawn.ps1`. `openclaw agents add` creates an isolated agent; its allowlist excludes `manage-inboxes`; ≤1 inbox env var visible.
8. **ClawHub-avoidance** — `scripts/phase0/check_clawhub_refs.py`. `clawhub_references=0` across config + skills + vault-schema + orchestrator.

**Exit criterion:** all eight exit 0. Any failure blocks the build.

### Phase 1 — memory foundation
Create the vault schema (`vault-schema/`), enable the Local REST API plugin, confirm localhost binding and that `enableInsecureServer` is false, store the key in `.env`, and re-run gates 4–5. Deliverable: a lead note that can be created, patched, read back, and blocked.

### Phase 2 — ingestion, no sending
Lead ingestion and the normalized lead-note writer. Handle CSV, PDF, and inconsistent directory/Google-Maps-style exports. **Deliverable: `Outreach/Leads/*.md` populated with `source` + `source_ref` provenance, `DRY_RUN=true`, zero send capability wired.**

### Phase 3 — deterministic compliance state machine
Wire `compliance_gate.evaluate()` into the graph as a pre-send node, plus the `Operations/Sender-Health/` and `Operations/Inference/` writers. Re-run gates 5 and 6. **Deliverable: every terminal state provably blocks, with the reason recorded in Obsidian.**

### Phase 4 — OAuth-only sender wrapper
Stand up `mcp-servers/email-outreach` over stdio, implement the real token minting for whichever providers passed Phase 0, add **dry-run** and **one-recipient** test modes. **Deliverable: a single real email to the operator's own address, with `Run Log` evidence and a `message_id`.**

### Phase 5 — reply ingestion and classification
Reply ingestion via the passing provider's REST read API, classification with SalesGPT's `determine_conversation_stage()` in the pre-generation hook, and **terminal suppression behaviour**: an unsubscribe reply writes `unsubscribed: true` and the next send attempt blocks. **Deliverable: a closed loop where a reply changes the lead's future behaviour.**

### Phase 6 — Paperclip adapter and watchdog
Deploy `paperclip-adapter/` (`openclaw_gateway` + `process`) and `watchdog/`. Verify dedupe over 30 minutes and that incident notes land in `Operations/Incidents/`. **Deliverable: a killed worker produces exactly one incident note and one toast.**

### Phase 7 — read-only supervisor chat
Mount the read-only console with Obsidian + Paperclip reads, no write tools. **Deliverable: it answers "why was lead X blocked" by quoting the gate's own reason string.**

### Phase 8 — autonomous low-volume sending
Set `DRY_RUN=false`, `SEND_WARMUP_STAGE=1`, cap 2/day/identity. **Expand only on outcome metrics:** to stage 2 (7/day) at `min_replies: 3`, `max_bounce_rate: 0.02`, `min_days_in_stage: 3`; to stage 3 (12/day) on the same criteria. Hard ceiling 17/day/identity is never exceeded. **Deliverable: sustained autonomous sending with the ladder enforced by config, not by operator attention.**
